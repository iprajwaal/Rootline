orders-worker OOM runbook

Created by Jonas Weber, last modified on 2026-07-03

Summary

The month-end report batch ran inside orders-worker and loaded every order of the month into memory. Workers hit their 512Mi limit and were killed again and again for just over an hour.

What happened

orders-worker pods were killed with "orders-worker container killed: OOMKilled (exit code 137)" every few minutes. Each restart paused the consumer group and order confirmations backed up.

Why it happened

  • The month-end batch loaded all orders of the month into worker memory at once.
  • The batch ran inside orders-worker, so its memory use killed the order consumer too.

Follow-ups

  • Move the month-end batch to its own scheduled job. (Orders team)
  • Read orders in pages of 1,000 in the batch. (Orders team)

Stop orders-worker from being killed for memory and get orders flowing again.

When to use

Use this when the OrdersWorkerOOMKilled alert fires, or worker pods show "orders-worker container killed: OOMKilled (exit code 137)".

Steps

#What to doCommandExpected
1Check worker memory.kubectl -n shop top pod -l app=orders-workerOne or more workers close to the 512Mi limit.
2Check how often the workers restart.kubectl -n shop get pods -l app=orders-workerRESTARTS above 2 in the last hour.
3Restart the workers.kubectl -n shop rollout restart deploy/orders-workerPods restart and memory drops.
4If restarts continue, roll back the worker release.kubectl -n shop rollout undo deploy/orders-workerThe previous worker version is running.

Contacts

  • Page the orders team if workers still restart after step 4.
