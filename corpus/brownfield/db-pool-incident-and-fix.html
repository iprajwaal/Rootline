Orders API 503s in June, what happened and how to fix it

Created by Priya Nair, last modified on 2025-06-06

Summary

For 38 minutes orders-api could not get database connections and returned 503 on about 12% of checkout requests. A new sales report endpoint held connections while it ran slow queries.

What happened

orders-api returned 503 on a share of checkout requests. Its logs showed "psycopg_pool.PoolTimeout: couldn't get a connection after 30.00 sec". Every pod had all 20 pool connections in use, and most of them were running the same reporting query.

Timeline

Time (UTC)WhatWho
2025-06-03 08:55orders-api 4.18 released with the new sales report endpoint. None at the time.Orders team
2025-06-03 09:12Alert OrdersDbPoolExhausted fired. Logs showed PoolTimeout errors. On-call acknowledged and opened an incident channel.SRE on-call

2025-06-03 09:36Checkout still failing. Raised DB_POOL_MAX to 50 on orders-api.SRE on-call
2025-06-03 09:50Error rate back under 1%. Disabled the sales report endpoint with its feature flag.Orders team

Why it happened

  • The sales report query held pool connections for up to 90 seconds with no statement timeout.
  • Reports and checkout shared one pool of 20 connections per pod, so reports could starve checkout.

Follow-ups

  • Add an alert at 80% pool usage. (SRE team)
  • Set a 30 second statement timeout on report queries. (Orders team)
  • Write SOP-DB-001 for pool exhaustion. (Priya Nair)
  • Move reports to a read replica with its own pool. (Orders team)

Restore orders-api when every connection in its database pool is in use and requests fail while waiting for a connection.

When to use

Use this procedure when the OrdersDbPoolExhausted alert fires, or when orders-api returns 503 and logs "psycopg_pool.PoolTimeout: couldn't get a connection after 30.00 sec".

Steps

#What to doCommandExpected
1Confirm the API is failing on pool timeouts.kubectl -n shop logs deploy/orders-api --since=15mRepeated PoolTimeout lines in the last 15 minutes.
2Count open database connections.psql -h orders-db -U shop -c "select count(*) from pg_stat_activity"The count is at or near 20 times the number of orders-api pods.
3List long running queries that hold connections.psql -h orders-db -U shop -c "select pid, now() - query_start as age, query from pg_stat_activity where state <> 'idle' order by age desc limit 10"Any query older than 60 seconds is posted in the incident channel with its pid.
4Raise the pool limit.kubectl -n shop set env deploy/orders-api DB_POOL_MAX=50The rollout completes and new pods start with DB_POOL_MAX=50.
5Confirm the API is healthy.curl -s http://orders-api:8080/healthStatus ok and orders-db ok.

Rollback

  1. Set the pool limit back once the long running queries are fixed. kubectl -n shop set env deploy/orders-api DB_POOL_MAX=20

Contacts

  • Page the orders team lead if the error rate is above 5% after step 5.
  • Page the database on-call if orders-db rejects connections or a query cannot be stopped.
